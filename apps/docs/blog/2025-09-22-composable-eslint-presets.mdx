Most ESLint <Terminology title="single-file config" to="/docs/quickstart/terminology#builds-and-tooling" color={true}>flat configs</Terminology> start the same way. You spread a popular shared config into your array, add your overrides, and move on.

But as the project grows — more <Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspaces</Terminology>, more file types, more framework-specific needs — the config grows with it. You end up with a single array where language rules, environment globals, and framework conventions are tangled together, and figuring out which object added which rule means reading the whole thing top to bottom.

Nova's <Terminology title="config layer" to="/docs/quickstart/terminology#nova-concepts" color={true}>presets</Terminology> are designed to keep that clean. Each <Terminology title="config layer" to="/docs/quickstart/terminology#nova-concepts" color={true}>preset</Terminology> handles one concern, and you compose them into exactly the combination your <Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspace</Terminology> needs.

## The Problem with Monolithic Configs

Even with <Terminology title="single-file config" to="/docs/quickstart/terminology#builds-and-tooling" color={true}>flat config</Terminology>, shared <Terminology title="config layer" to="/docs/quickstart/terminology#nova-concepts" color={true}>presets</Terminology> tend to ship as one large array that covers everything. You spread it in and get hundreds of rules — some relevant, some not.

When a rule behaves unexpectedly, you trace through the shared config to figure out where it came from. When two <Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspaces</Terminology> need different rules, you fork the config or add per-<Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspace</Terminology> overrides.

The config stays flat, but the complexity doesn't.

## Layers, Not Inheritance

Nova's <Terminology title="config layer" to="/docs/quickstart/terminology#nova-concepts" color={true}>presets</Terminology> are independent arrays. Each one handles a specific concern, and you spread them into your config in any order:

```javascript
import {
  dxCodeStyle,
  langTypescript,
  runtimeNode,
} from '@cbnventures/nova/presets/eslint';

export default [
  ...dxCodeStyle,
  ...langTypescript,
  ...runtimeNode,
];
```

Three layers, each self-contained:

- **Code style** (`dxCodeStyle`) — Conventions, formatting, and structural patterns that apply everywhere
- **Language** (`langTypescript`) — TypeScript-specific rules and parser configuration
- **Environment** (`runtimeNode`) — Node.js globals, module resolution, and platform constraints

A browser project uses `runtimeBrowser` instead of `runtimeNode`. A Docusaurus site adds `fwDocusaurus` on top.

Each <Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspace</Terminology> composes exactly the layers it needs.

## What Each Layer Does

### Code Style

The `dxCodeStyle` layer covers rules that apply regardless of language or environment: naming conventions, import ordering, comment formatting, and structural patterns. These are the rules that keep a codebase consistent across every file.

### Language

Language layers configure the parser and add language-specific rules. `langTypescript` sets up `@typescript-eslint/parser`, enables type-aware rules, and configures strictness.

`langJavascript` and `langMdx` do the same for their respective file types.

### Environment

Environment layers add globals and module settings for a specific runtime. `runtimeNode` adds Node.js globals and <Terminology title="CJS" to="/docs/quickstart/terminology#javascript-and-typescript" color={true}>CommonJS</Terminology>/<Terminology title="ECMAScript Modules" to="/docs/quickstart/terminology#javascript-and-typescript" color={true}>ESM</Terminology> resolution.

`runtimeBrowser` adds DOM globals. `runtimeEdge` covers edge runtimes like Cloudflare Workers.

### Framework

Framework layers add rules specific to a framework's patterns. `fwNextjs` handles Next.js conventions.

`fwExpressjs` handles Express. `fwDocusaurus` handles Docusaurus.

You only add the one you need.

## The TSConfig Side

The same layering applies to TypeScript configuration. Nova ships TSConfig <Terminology title="config layer" to="/docs/quickstart/terminology#nova-concepts" color={true}>presets</Terminology> that compose the same way — a strict baseline, an environment target, and an optional framework layer:

```json
{
  "extends": [
    "@cbnventures/nova/presets/tsconfig/dx-essentials.json",
    "@cbnventures/nova/presets/tsconfig/dx-strict.json",
    "@cbnventures/nova/presets/tsconfig/runtime-node.json"
  ]
}
```

No guessing which `compilerOptions` came from where. Each <Terminology title="config layer" to="/docs/quickstart/terminology#nova-concepts" color={true}>preset</Terminology> handles one concern.

## Why This Matters

The point isn't that composition is better than inheritance in the abstract. The point is that <Terminology title="multi-package repo" to="/docs/quickstart/terminology#git-and-workflow" color={true}>monorepos</Terminology> have diverse <Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspaces</Terminology> — an API server, a docs site, a <Terminology title="command line interface" to="/docs/quickstart/terminology#fundamentals" color={true}>CLI</Terminology> tool, a shared library — and each one needs a different combination of rules.

Composable layers make that easy without maintaining a dozen forked configs.

One language layer. One environment.

One framework if you need it. The same code style everywhere.

See the full [preset documentation](/docs/presets/eslint/best-practices/) for the complete list of available layers and what each one configures.
