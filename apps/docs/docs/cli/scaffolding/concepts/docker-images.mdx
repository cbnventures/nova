Package a Nova monorepo as one repository-wide s6-overlay container appliance while keeping Docker support optional.

## Why Use This Contract?

1. Keeps one container boundary per repository so every workspace contributes to the same deployable appliance.
2. Uses the same s6 service model for one service or many so the image can expand without changing its structure.
3. Builds from the repository root so services can consume any workspace they depend on without copying artifacts from a host build.

## Repository Boundary

Nova supports exactly one generated container image per repository. Publishing several independent container images from one repository is unsupported.

That image can contain any number of native s6-rc longruns and oneshots:

- One workspace can contribute several supervised services.
- Several workspaces can contribute services to the same appliance.
- Auxiliary services can run beside the primary application services.
- A single-service or documentation-only image keeps the same s6 structure.

Docker remains opt-in. Selecting Docker for a supported scaffold contributes that workspace to the repository's one appliance without changing its non-container deployment choices.

## Generated Layout

Docker-enabled repositories keep the public build entry points at the project root and the private assembly files in one workspace:

```text
.
├── .dockerignore
├── Dockerfile
├── compose.yml
├── apps/
└── packages/
    └── docker/    # Private image assembly and s6 service definitions
```

The root `Dockerfile` uses the repository root as its build context. The private `packages/docker` workspace assembles the root filesystem and service graph; it is not a separately published package or image.

Native service definitions live beneath `packages/docker/rootfs/etc/s6-overlay/s6-rc.d/<service>`. Their activation markers live separately beneath `packages/docker/rootfs/etc/s6-overlay/user-bundles.d/user/contents.d/<service>`, which is the current s6-overlay user-bundle interface. Do not place the `user` bundle inside `s6-rc.d`; that legacy-compatible location is deprecated by s6-overlay.

:::warning Workspace-local Docker layouts are unsupported

Nova does not retain compatibility with generated `Dockerfile`, `compose.yml`, or `.dockerignore` files inside individual workspaces.
:::

## Runtime Contract

Every generated image starts as root through s6-overlay's `/init`. Initialization prepares persistent storage and then each non-root service uses `s6-applyuidgid` with the configured numeric identity.

| Variable                     | Default             | Purpose                                                                |
|------------------------------|---------------------|------------------------------------------------------------------------|
| `PUID`                       | `1000`              | Numeric service user ID. The accepted range is `1` through `60000`.    |
| `PGID`                       | `1000`              | Numeric service group ID. The accepted range is `1` through `60000`.   |
| `TZ`                         | `UTC`               | Installed IANA timezone used for `/etc/localtime` and `/etc/timezone`. |
| `NOVA_STATE_DIRECTORY`       | Resolved at startup | Active app-state directory, normally `/config`.                        |
| `NOVA_KEYS_DIRECTORY`        | Resolved at startup | Private key directory inside app state.                                |
| `NOVA_INSTALLATION_KEY_FILE` | Resolved at startup | Installation key path. The application creates the key itself.         |
| `NOVA_DATABASE_DIRECTORY`    | Resolved at startup | SQLite parent directory or PostgreSQL data directory.                  |

Startup rejects identity values outside the accepted range and unknown or unsafe timezone names. It links `/etc/localtime` to the selected zoneinfo entry and writes `/etc/timezone` before any application service starts.

Application ports are fixed numbers, not runtime environment variables. Each service listens on the numeric `services[].port` declared by the assembly manifest. The generated Dockerfile exposes that port, and bridge-mode Compose maps the same host port to it by default. To use another host port, change only the left side of the mapping, such as `"8080:22604"`. Host networking has no mapping layer, so the service always uses its fixed port.

### Persistent State

Mount application state at `/config`. Files a user imports, downloads, or otherwise manages as content remain beneath `/data` and are not part of the app-state mount.

Initialization creates this standard layout beneath the resolved state directory:

```text
<state-directory>/
├── database/
└── keys/                         # mode 0700
    └── installation.key          # mode 0600 when the app creates it
```

The initializer creates and permissions the directories but does not create `installation.key`. On every start, it recursively changes ownership of the complete state directory to `PUID:PGID`, and changes ownership of each service `writablePaths` entry itself, without descending into it, so content folders such as downloads under `/data` are never walked. It then restores mode `0700` on `keys/` and mode `0600` on every regular file below it.

The manifest can map the resolved state directory to one additional application-specific variable with `stateEnvironment`. Services receive that variable together with the four `NOVA_*` paths through `/run/nova-docker/environment`.

### Legacy `/data` Migration

`legacyStatePaths` identifies relative files or directories that prove an older install stores app state beneath `/data`. Nova uses those markers as follows:

1. If `/config` is a mountpoint, its markers are absent, and `/data` has markers, initialization moves each declared entry into `/config`.
2. A same-filesystem move uses `rename`; a cross-filesystem move copies metadata, verifies the copy, renames the verified temporary entry into place, and only then removes the source.
3. Existing destinations are never overwritten. If both locations contain state, `/config` wins and initialization logs a warning.
4. If `/config` is not a mountpoint and only `/data` contains state, the appliance keeps using `/data` for that start and logs one warning recommending that the app-state mount move to `/config`.

Declare only safe, specific relative markers such as `settings.json` or `database/app.sqlite`. An empty marker list disables legacy detection while new installs still use `/config`.

## Assembly Manifest

`packages/docker/manifest.json` is the source of truth for the appliance-level runtime contract. Nova preserves manifests created before these fields existed and fills in the current defaults when it next generates the assembly.

| Field                      | Default      | Purpose                                                              |
|----------------------------|--------------|----------------------------------------------------------------------|
| `healthPath`               | `/health`    | Absolute path requested from the first port-bearing HTTP longrun.    |
| `legacyStatePaths`         | `[]`         | Relative app-state markers eligible for migration from `/data`.      |
| `networkMode`              | `host`       | Compose network mode; `bridge` enables generated port mappings.      |
| `stateEnvironment`         | None         | Optional app-specific alias for `NOVA_STATE_DIRECTORY`.              |
| `services[].critical`      | `false`      | Halts the container after a non-zero or abnormal service exit.       |
| `services[].port`          | Profile port | Fixed container port, from `1` through `65535` and unique per image. |
| `services[].writablePaths` | `[]`         | Additional absolute paths whose top level is owned by `PUID:PGID`.   |

For example:

```json
{
  "healthPath": "/health",
  "legacyStatePaths": [
    "settings.json",
    "database/app.sqlite"
  ],
  "networkMode": "host",
  "schemaVersion": 1,
  "services": [
    {
      "command": "node build/index.js",
      "critical": true,
      "dependencies": [],
      "environment": {},
      "kind": "longrun",
      "name": "app",
      "port": 22604,
      "requiredForHealth": true,
      "runAsRoot": false,
      "workspace": "apps/app",
      "writablePaths": []
    }
  ],
  "stateEnvironment": "APP_STATE_DIRECTORY",
  "workspaces": []
}
```

Every numeric service port must be unique within the image. The generated Dockerfile emits literal `EXPOSE` instructions, service commands and health checks use the same literal values, and bridge-mode Compose emits fixed `"PORT:PORT"` mappings. Host mode does not emit `ports` mappings.

Nova ignores the retired top-level `ports` map and retired `services[].portEnvironment` keys when it reads an older manifest. It prints one notice that ports are fixed and that those keys can be removed, then writes the current manifest without them.

## Supervision, Health, and Shutdown

The generated Dockerfile configures a 30-second health interval, 5-second timeout, 30-second start period, and three retries. Its one generated helper:

1. Runs `/etc/nova-docker/healthcheck` instead when that executable project override exists.
2. Requires every declared s6 longrun to report `up`.
3. Sends `GET` to the fixed port of the first port-bearing longrun, such as `http://127.0.0.1:22604/health`, and accepts only a `2xx` response.

The legacy `services[].requiredForHealth` field remains readable for older manifests, but it no longer excludes a longrun from supervision health. Every longrun must be up.

`critical: true` adds a finish script that halts the container after a non-zero exit or signal so Docker's restart policy can restart the whole appliance cleanly. Non-critical longruns remain under normal s6 restart supervision.

Stage-two failures stop the image instead of leaving a partially started appliance. Generated longruns receive six seconds to stop before `SIGKILL`; finish and final-kill windows are one second each so shutdown remains below Docker's default ten-second stop timeout.

## Log Lines

Generated scripts write one plain-text fact per line with this shape:

```text
2026-01-15T18:42:07Z INFO component: message
```

The level is one of `DEBUG`, `INFO`, `WARN`, or `ERROR`, and timestamps are UTC ISO-8601 values ending in `Z`. Application code should use the same shape. Shell services can source `/usr/local/libexec/nova-docker/log` and call `nova_log INFO app "message"`, or invoke the helper directly with the same three arguments.

## Installation

The generated image expects a root start and drops privileges inside s6. A host-network install can use this form:

```sh
sudo docker rm --force example-app && \
sudo docker rmi example/example-app:latest && \
sudo docker run \
    -d \
    -v "/srv/example-app/config:/config" \
    -e "PGID=1000" \
    -e "PUID=1000" \
    -e "TZ=America/New_York" \
    --restart always \
    --user 0:0 \
    --net=host \
    --name example-app \
    example/example-app:latest
```

When a manifest opts into bridge mode, place each required `-p` flag after the environment flags and use `--net=bridge`. Keep the fixed container port on the right and select the host port on the left, such as `-p "8080:22604"`. Add `--cap-add` or `--device` flags in that same position only when the application requires them. The generated default does not add capabilities, devices, a read-only root, `tmpfs`, capability drops, `no-new-privileges`, or shared-memory overrides.

With host networking, no host-to-container mapping exists. The appliance listens on its fixed container port, such as `22604`.

The equivalent host-network Compose file is:

```yaml
services:
  app:
    image: example/example-app:latest
    environment:
      PGID: "1000"
      PUID: "1000"
      TZ: "America/New_York"
    network_mode: host
    restart: always
    user: "0:0"
    volumes:
      - "/srv/example-app/config:/config"
```

For bridge mode, change `network_mode` to `bridge` and add a `ports` entry for each fixed container port. The generated mapping uses the same value on both sides, such as `"22604:22604"`. Change only the host side to publish it elsewhere:

```yaml
services:
  app:
    ports:
      - "8080:22604"
```

## OCI Image Labels

The generated runtime image carries OCI annotations from `nova.config.json`:

| Label                                    | Nova config source                   |
|------------------------------------------|--------------------------------------|
| `org.opencontainers.image.title`         | `project.name.title`, then its slug. |
| `org.opencontainers.image.description`   | `project.description.short`.         |
| `org.opencontainers.image.url`           | `urls.homepage`.                     |
| `org.opencontainers.image.source`        | `urls.repository`.                   |
| `org.opencontainers.image.documentation` | `urls.documentation`.                |
| `org.opencontainers.image.licenses`      | `project.license`.                   |
| `org.opencontainers.image.vendor`        | `project.legalName`.                 |

Nova escapes project-controlled values for Dockerfile double-quoted label syntax when it scaffolds or refreshes the shared Dockerfile. Missing optional metadata produces an empty label value rather than leaving a scaffold token unresolved.

The publish workflow adds `org.opencontainers.image.version` from the release, manual, or Git reference and `org.opencontainers.image.revision` from `github.sha` while building the immutable OCI artifact. Those build-time labels travel with the same digest that Docker Hub and GitHub Container Registry receive.

## Build and Distribution

The root `Dockerfile` compiles container inputs inside named stages and copies only runtime output into the final s6 image. The build stage includes the root `nova.config.json` so workspace builds can resolve shared Nova identity and project settings. A host-side workspace build is not an input to the container build.

The private `packages/docker` workspace connects the appliance to the normal repository lifecycle. Its `check` command validates the root Dockerfile with BuildKit, and its `build` command builds the root Compose image. Root `npm run check` and `npm run build` therefore exercise the container contract instead of silently skipping the Docker workspace.

Workspace files needed after compilation are declared as workspace-relative runtime paths in the private assembly manifest. Nova copies those paths from the build stage into the same `/app/apps/...` or `/app/packages/...` runtime workspace; generated root Dockerfiles are not extended with hand-maintained `COPY` instructions.

Non-container deliverables continue through the normal workspace pipeline. If one workspace feeds both the container and another destination, it compiles once for each deliverable because the two outputs have independent build boundaries.

Container publishing builds one OCI artifact once for the workflow's selected platforms. `linux/amd64` and `linux/arm64` are supported, and selecting both produces one multi-platform artifact. Docker Hub and GitHub Container Registry jobs distribute that same artifact instead of rebuilding registry-specific images. Before that build, the publish workflow's check step runs `check` for every workspace the image ships, `packages/docker`, and the root's own checks.

## Documentation-Only Example

A repository containing only a Docusaurus workspace can still opt into Docker. The result is one s6-overlay image whose supervised static service serves the compiled documentation site.

GitHub Pages and Cloudflare Pages remain independent destinations. You can publish the same Docusaurus workspace to either or both Pages targets in addition to the container image; choosing one target does not disable the others.

See [Workflows](/docs/cli/generators/github/workflows#publishing-container-images) for the registry configuration contract.
