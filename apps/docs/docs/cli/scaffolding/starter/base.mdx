Scaffold a **base <Terminology title="multi-package repo" to="/docs/quickstart/terminology#git-and-workflow" color={true}>monorepo</Terminology>** project with workspaces configuration, ready for adding framework workspaces. This command is optional: use it when you want the project root now but do not want to choose an app or documentation framework yet.

| What you want now                 | Command to start with           | Result                          |
|-----------------------------------|---------------------------------|---------------------------------|
| Only an empty Nova monorepo root  | `nova scaffold starter base`    | Root, `apps/`, and `packages/`  |
| A root and the first app together | `nova scaffold app <framework>` | Root plus the app workspace     |
| A root and documentation together | `nova scaffold docs docusaurus` | Root plus the docs workspace    |
| A root and a package together     | `nova scaffold package <type>`  | Root plus the package workspace |

You do not need to run `starter base` before a direct app, docs, or package command.

## Why Use This Command?

1. Creates the root `package.json` with `workspaces` configured for `apps/*` and `packages/*` so you can add workspaces immediately.
2. Creates a root `turbo.json` and standard `dev`, `prod`, `check`, `build`, `deploy`, and `clean` script groups. Each top-level script delegates to its adjacent `name:*` Turbo step through `nova utility run-scripts`; development and production-oriented groups pass an explicit `--node-env` value.
3. Pins the npm and Node.js toolchain used by current Nova projects and records explicit install-script decisions used by the built-in scaffolds.
4. Generates a baseline `nova.config.json` with the project name, current starting year, and `Example Company` legal-name placeholder so recipes, utilities, and identity-aware workspaces have valid input from the start.
5. Registers the root environment namespace and generates `.env` plus `.env.sample` with Nova's Node.js and logging defaults.
6. Generates Nova's canonical root `.gitignore` for secrets, dependencies, build output, editor metadata, and supported platform tooling.
7. Installs `@cbnventures/nova` as a dependency so its CLI, presets, and runtime toolkit remain available to generated workspaces.
8. Adds root Vitest coverage for dotenv formatting and the private monorepo coordinator contract, backed by Nova's shared test setup.

## Requirements

- **Node.js runtime** — Use any Node.js <Terminology title="long term support" to="/docs/quickstart/terminology#fundamentals" color={true}>LTS</Terminology> release.
- **Start outside a project** — Run the command where Nova cannot find a `package.json`. The selected output may already contain unrelated files, but Nova refuses to replace `package.json` or `nova.config.json`.

## Options

| Flag                | Description                                                  |
|---------------------|--------------------------------------------------------------|
| `-d, --dry-run`     | Run without writing any files.                               |
| `--install`         | Install dependencies after scaffolding; this is the default. |
| `--no-install`      | Skip dependency installation.                                |
| `--name <name>`     | Project name.                                                |
| `--non-interactive` | Require every answer as a flag and do not open prompts.      |
| `--output <dir>`    | Output directory.                                            |

## How It Works

### Interactive Wizard

When run without flags, the command collects the project details before writing anything:

1. **Project name** — Enter a slug for your monorepo (e.g. `my-app`).

Nova creates the project in `./{project-name}` by default, displays the complete plan, and asks for one confirmation. A new project never writes directly into the current directory. Dependencies install after the files are ready unless you pass `--no-install`. Project-level generators remain separate commands that you can run after configuring `nova.config.json`.

### Non-Interactive Mode

Agents and automation should add `--non-interactive` and provide `--name`. `--output` is optional and defaults to `./{project-name}`. Nova validates the complete plan before writing and installs dependencies unless the command includes `--no-install`.

<Tabs groupId="install-state">
  <TabItem value="nova" label="nova (installed)" default>

    ```bash
    nova scaffold starter base --non-interactive --name my-app --output ./my-app
    ```

  </TabItem>
  <TabItem value="npx" label="npx (no install)">

    ```bash
    npx --yes @cbnventures/nova@latest scaffold starter base --non-interactive --name my-app --output ./my-app
    ```

  </TabItem>
</Tabs>

## Safety Checks

Before creating any file, Nova validates the project slug and checks every root path it owns, including `.gitignore`, `package.json`, `nova.config.json`, and `turbo.json`. If any target file already exists, the command stops and lists the conflict. `--dry-run` performs the same validation and reports the exact root path without writing.

## Next Steps

After scaffolding, enter the new monorepo and add as many workspaces as the project needs. Each scaffold command detects the existing workspace root, creates only the requested workspace, and adds it to the same `nova.config.json`. Running another scaffold command later preserves the workspaces that are already registered.

For example, these commands add a Docusaurus documentation site and a Cloudflare Worker to one project:

<Tabs groupId="install-state">
  <TabItem value="nova" label="nova (installed)" default>

    ```bash
    cd my-app
    nova scaffold docs docusaurus
    nova scaffold app cloudflare-workers
    ```

  </TabItem>
  <TabItem value="npx" label="npx (no install)">

    ```bash
    cd my-app
    npx --yes @cbnventures/nova@latest scaffold docs docusaurus
    npx --yes @cbnventures/nova@latest scaffold app cloudflare-workers
    ```

  </TabItem>
</Tabs>

You can mix any supported app, docs, and package scaffolds this way. Run each command from the monorepo root, not from inside an existing workspace.

Once the workspaces are in place, run generators for additional project-level files like `.editorconfig`, `LICENSE`, and `README.md`. The root `.gitignore` is already generated by the scaffold.
