Every <Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspace</Terminology> in a Nova <Terminology title="multi-package repo" to="/docs/quickstart/terminology#git-and-workflow" color={true}>monorepo</Terminology> is classified by a **role** and a **policy**.

These two properties, defined in <Terminology title="Nova config" to="/docs/quickstart/terminology#nova-concepts" color={true}>`nova.config.json`</Terminology>, control how <Terminology title="transform script" to="/docs/quickstart/terminology#nova-concepts" color={true}>recipes</Terminology> read, create, modify, and remove fields in each workspace's `package.json`.

## Roles

A role describes what the workspace _is_. It determines which `package.json` fields are allowed, which are removed, and which are created when missing.

| Role       | Purpose                                                                                                                                                           |
|------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `project`  | The monorepo root. Owns the `workspaces` array, `packageManager`, and dependency install-script policy.                                                           |
| `docs`     | A documentation site (e.g., Docusaurus). Does not publish to a package registry.                                                                                  |
| `config`   | A shared configuration package (e.g., ESLint presets, TSConfig presets). Retains the `types` and `module` bundler convention fields.                              |
| `app`      | An application workspace (e.g., a web app, an API server). Not intended for registry publishing.                                                                  |
| `package`  | A publishable library. Retains artifact fields (`files`, `bin`, `man`, `directories`) and bundler convention fields (`types`, `module`, `sideEffects`, `esnext`). |
| `tool`     | An internal CLI tool. Similar to `package` but does not retain `sideEffects` or `esnext`.                                                                         |
| `template` | A template workspace used by scaffolding commands. Not intended for registry publishing.                                                                          |

### Role-Gated Fields

The following table shows which `package.json` fields are retained or removed based on role. Fields not listed here are handled independently of role.

| Field         | Retained by                 | Removed from all others |
|---------------|-----------------------------|-------------------------|
| `workspaces`  | `project`                   | Yes                     |
| `files`       | `package`, `tool`           | Yes                     |
| `bin`         | `package`, `tool`           | Yes                     |
| `man`         | `package`, `tool`           | Yes                     |
| `directories` | `package`, `tool`           | Yes                     |
| `types`       | `config`, `package`, `tool` | Yes                     |
| `module`      | `config`, `package`, `tool` | Yes                     |
| `sideEffects` | `package`                   | Yes                     |
| `esnext`      | `package`                   | Yes                     |

### Root Package Manager

The `project` workspace is the only workspace allowed to own `packageManager`. Use one exact Corepack descriptor:

| Client | Root `package.json` shape          |
|--------|------------------------------------|
| npm    | `"packageManager": "npm@11.18.0"`  |
| pnpm   | `"packageManager": "pnpm@10.17.1"` |
| Yarn   | `"packageManager": "yarn@4.9.4"`   |

Nova uses this field as executable configuration, not just metadata. Publish workflow generation selects the matching client for dependency installation, local package executables, and project scripts. A missing, partial, ranged, or unsupported descriptor is invalid for publish generation, which stops before changing workflow files. The [`sync-environment` recipe](/docs/cli/recipes/package-json/sync-environment) can repair the root field and removes duplicate copies from child workspaces.

The package manager is separate from a publish destination. For example, a Yarn-managed project can still deploy a package to the `npm` target; Yarn manages the project, while the target identifies the registry operation.

### Root Install-Script Policy

An npm-managed project keeps its dependency lifecycle-script decisions in the root `allowScripts` object. Each entry answers one security question: may this installed dependency run `preinstall`, `install`, `postinstall`, or a source-package `prepare` script?

```json
{
  "allowScripts": {
    "core-js": false,
    "node-pty@1.1.0": true
  }
}
```

Use an exact `name@version` key for an approval so a future dependency upgrade requires a new review. Use a name-only `false` entry for an explicit denial. A missing entry is unreviewed: npm 11 reports it while still running the script, whereas npm 12 blocks it by default.

Nova recognizes and preserves non-empty `allowScripts` objects but never infers that dependency code is trustworthy. Review the pending set with the command that belongs to the npm version pinned by `packageManager`:

<Tabs groupId="npm-install-script-policy">
  <TabItem value="npm-11" label="npm 11" default>

    ```bash
    npm approve-scripts --allow-scripts-pending
    ```

  </TabItem>
  <TabItem value="npm-12" label="npm 12">

    ```bash
    npm install-scripts ls
    ```

  </TabItem>
</Tabs>

Both commands above are read-only. Approve or deny a package only after reviewing its lifecycle commands and verifying the project without them.

## Policies

A policy describes how the workspace is **versioned and published**. It determines whether the workspace is locked, tracked, or released to a registry.

| Policy          | Version behavior                        | Publishing               | `private` value |
|-----------------|-----------------------------------------|--------------------------|-----------------|
| `freezable`     | Locked at `0.0.0`. Never incremented.   | Never published.         | `true`          |
| `trackable`     | Tracked via semver. Can be incremented. | Never published.         | `true`          |
| `distributable` | Tracked via semver. Can be incremented. | Published to a registry. | `false`         |

### Policy-Gated Fields

The following table shows which `package.json` fields are retained or removed based on policy. Fields not listed here are handled independently of policy.

| Field           | Retained by     | Removed from all others |
|-----------------|-----------------|-------------------------|
| `description`   | `distributable` | Yes                     |
| `keywords`      | `distributable` | Yes                     |
| `homepage`      | `distributable` | Yes                     |
| `bugs`          | `distributable` | Yes                     |
| `author`        | `distributable` | Yes                     |
| `contributors`  | `distributable` | Yes                     |
| `funding`       | `distributable` | Yes                     |
| `repository`    | `distributable` | Yes                     |
| `publishConfig` | `distributable` | Yes                     |

### Allowed Policies by Role

Not every policy is available to every role. The following table shows which policies each role supports:

| Role       | `freezable` | `trackable` | `distributable` |
|------------|-------------|-------------|-----------------|
| `project`  | Yes         |             |                 |
| `docs`     | Yes         | Yes         |                 |
| `config`   | Yes         | Yes         |                 |
| `app`      |             | Yes         |                 |
| `package`  |             | Yes         | Yes             |
| `tool`     | Yes         | Yes         |                 |
| `template` | Yes         | Yes         |                 |

## Workspace Naming

Each workspace's `name` (the value written to its `package.json`) must follow a role-specific pattern. The parser silently drops workspaces whose names do not match, so a typo here is a quiet foot-gun.

Patterns reference the project slug from `project.name.slug`. When the slug is not set, the prefix falls back to the literal role name.

| Role       | Required pattern                                                                                                                   |
|------------|------------------------------------------------------------------------------------------------------------------------------------|
| `project`  | Exactly `"{slug}-project"`, or `"project"` when no slug is set.                                                                    |
| `docs`     | Exactly `"{slug}-docs"`, or `"docs"` when no slug is set.                                                                          |
| `config`   | `"{slug}-config-{descriptor}"`, or `"config-{descriptor}"` when no slug is set. The descriptor must match the simple slug pattern. |
| `app`      | `"{slug}-app-{descriptor}"`, or `"app-{descriptor}"` when no slug is set. The descriptor must match the simple slug pattern.       |
| `tool`     | `"{slug}-tool-{descriptor}"`, or `"tool-{descriptor}"` when no slug is set. The descriptor must match the simple slug pattern.     |
| `package`  | Any name matching the simple slug pattern (e.g., `"my-lib"`) or the scoped npm pattern (e.g., `"@scope/my-lib"`).                  |
| `template` | Same as `package`: simple or scoped slug.                                                                                          |

The patterns are:

- **Simple slug**: `^[a-z0-9]+(?:[a-z0-9-_]*[a-z0-9])?$`. Lowercase letters, digits, hyphens, and underscores; must start and end with a letter or digit.
- **Scoped slug**: `^@[scope]/[name]$`, where both `scope` and `name` match the simple slug pattern.

## Required vs. Conditional

Each field that a <Terminology title="transform script" to="/docs/quickstart/terminology#nova-concepts" color={true}>recipe</Terminology> handles is classified as either **required** or **conditional**. This classification describes _when_ the recipe will act on the field.

| Classification  | Meaning                                                                                                                                                                                                                    |
|-----------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Required**    | The recipe ensures the field exists. If missing, it is created with a computed or default value. If invalid, it is corrected.                                                                                              |
| **Conditional** | The recipe only acts when the field is already present, or when a specific recipe setting, workspace role, or workspace policy triggers it. A conditional field is never created from nothing without an explicit trigger. |

### How to Read Recipe Documentation

In each recipe's **Behavior** section, every field is tagged with **(Required)** or **(Conditional)**:

- **`name` (Required)** means the recipe guarantees this field will exist after it runs. If the field is missing, the recipe creates it.
- **`description` (Conditional)** means the recipe will only touch this field if it is already present or if the workspace meets certain criteria (e.g., a specific policy and an enabled setting).

This distinction matters because **required** fields are safe to omit from a new `package.json` — the recipe will create them automatically.

**Conditional** fields, on the other hand, are only managed if they already exist or if you explicitly opt in through configuration.
