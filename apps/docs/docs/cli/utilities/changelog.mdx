Record individual changes and release versioned changelogs with a single command that guides you through each step.

## Summary

The `changelog` command combines two workflows into one guided flow:

- **Recording** a change (what happened).
- **Releasing** accumulated changes (bump versions and write a `CHANGELOG.md`).

In interactive mode, a menu lets you pick which action to take. In non-interactive mode, the `--record` and `--release` flags drive the same workflows from scripts and <Terminology title="continuous integration and deployment" to="/docs/quickstart/terminology#builds-and-tooling" color={true}>CI/CD</Terminology> pipelines.

Recorded entries are stored as individual `.md` files in a `.changelog/` directory at the <Terminology title="project root" to="/docs/quickstart/terminology#git-and-workflow" color={true}>monorepo root</Terminology>. When released, the entries are consumed, versions are bumped in each affected `package.json`, and a `CHANGELOG.md` is written (or updated) in the <Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspace</Terminology> directory.

## Why Use This Command?

- Combines the record-and-release lifecycle into one command instead of separate tools.
- Interactive prompts guide you through package selection, category, description, and <Terminology title="semantic versioning" to="/docs/quickstart/terminology#fundamentals" color={true}>SemVer</Terminology> bump type. No flags to memorize.
- The `--record` and `--release` flags enable the same workflow in <Terminology title="continuous integration and deployment" to="/docs/quickstart/terminology#builds-and-tooling" color={true}>CI/CD</Terminology> without prompts.
- The **dry run** option lets you preview every change before any file is touched.
- Supports both **<Terminology title="semantic versioning" to="/docs/quickstart/terminology#fundamentals" color={true}>SemVer</Terminology>** and **CalVer** strategies, configured per-project in `nova.config.json`.

## Use Cases

- **Solo projects** — Record a change and release it in the same session without learning a separate versioning tool.
- **Team workflows** — Each contributor records changes in their PR. A maintainer runs the release step when ready.
- **<Terminology title="continuous integration and deployment" to="/docs/quickstart/terminology#builds-and-tooling" color={true}>CI/CD</Terminology> automation** — Use `--record` in a pipeline step to capture changes, then `--release` in a publish step to bump versions and write changelogs.
- **Migration from Changesets** — Replace `changeset add` with `nova utility changelog --record` and `changeset version` with `nova utility changelog --release`.

## Requirements

- **Node.js runtime** — Use any Node.js <Terminology title="long term support" to="/docs/quickstart/terminology#fundamentals" color={true}>LTS</Terminology> release with either the installed `nova` <Terminology title="command line interface" to="/docs/quickstart/terminology#fundamentals" color={true}>CLI</Terminology> or `npx`.
- **Project root** — Run the command from the directory containing the top-level `package.json` (<Terminology title="multi-package repo" to="/docs/quickstart/terminology#git-and-workflow" color={true}>monorepos</Terminology> included).
- **Nova config** — A valid <Terminology title="Nova config" to="/docs/quickstart/terminology#nova-concepts" color={true}>`nova.config.json`</Terminology> must exist. Recording a change requires a non-<Terminology title="locked workspace" to="/docs/quickstart/terminology#nova-concepts" color={true}>freezable</Terminology> workspace; releasing can also stamp freezable workspaces when there are no entries.

## Options

| Flag                        | Description                                                                       |
|-----------------------------|-----------------------------------------------------------------------------------|
| `--record`                  | Record a change. Prompts for missing values unless all flags are provided.        |
| `--release`                 | Release accumulated changes.                                                      |
| `-p, --package <name>`      | Package name for recording.                                                       |
| `-c, --category <category>` | Category: `updated`, `fixed`, `added`, `removed`.                                 |
| `-b, --bump <type>`         | Bump type: `major`, `minor`, `patch`. Semver only — not available in CalVer mode. |
| `-m, --message <message>`   | Change description.                                                               |
| `-d, --dry-run`             | Run without writing any files.                                                    |

## How It Works

### Record Flow

1. **Select package** — Auto-selects if only one non-<Terminology title="locked workspace" to="/docs/quickstart/terminology#nova-concepts" color={true}>freezable</Terminology> <Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspace</Terminology> exists. Otherwise prompts.
2. **Select category** — Choose from Updated, Fixed, Added, or Removed.
3. **Enter description** — Free-text description of the change.
4. **Select bump type** — Pre-selected based on category (Added/Updated = minor, Fixed = patch, Removed = major). Override if needed. (Skipped in CalVer mode.)
5. **Save** — Writes an entry file to `.changelog/` with a random adjective-noun-verb filename.

### Release Flow

The validation and preview steps finish before Nova writes any release files. Version bumps and changelog updates run for releasing non-freezable workspaces, while sentinel stamping also runs for freezable workspaces; consumed entries are deleted only after every workspace succeeds.

1. **Read entries** — Collects all `.md` files from `.changelog/`.
2. **Validate release history** — Confirms the configured strategy agrees with the root and non-freezable workspace changelogs.
3. **Preflight lock-step versions** — When `settings.lockStepVersioning` is `true`, reads every non-freezable workspace's `package.json`, validates its version against the configured strategy, and confirms all of them start at the same version. Nova stops before writing if a file is missing, malformed, or drifted.
4. **Lock-step expansion** — Includes every non-freezable workspace in the release, even when it had no recorded entries. All workspaces move to the same computed version. Workspaces without entries receive a "No changes." section in their `CHANGELOG.md`.
5. **Show summary** — Lists entries grouped by package with the computed version bump (highest bump wins).
6. **Confirm** — Interactive only. Non-interactive mode (`--release`) skips this step.
7. **Bump version** — Updates the `version` field in each affected `package.json`.
8. **Write CHANGELOG.md** — Prepends a new version section. Creates the file if it does not exist.
9. **Sync exact package references** — Updates exact-pinned references to co-released packages in workspace and template `package.json` files. Ranges and workspace protocols are left unchanged.
10. **Stamp sentinels** — Replaces `@since UNRELEASED` and `@deprecated UNRELEASED` tags in each workspace's own `src/` and `scripts/` trees (`.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.mjs`, `.cjs`, and `.css` files). Releasing non-freezable workspaces use their new version, while freezable workspaces use `0.0.0` without a version bump or changelog. Prerelease versions (containing a hyphen) are skipped. A scanning or stamping failure leaves pending entries in place.
11. **Clean up** — Deletes consumed entry files from `.changelog/` only after every workspace has completed successfully.

When `.changelog/` has no entries, `--release` still stamps freezable workspaces at `0.0.0`. This includes the project root's `scripts/` files; it does not scan into sibling `apps/` or `packages/` workspaces. A dry run writes nothing.

:::danger Non-Zero Exit Code
The command exits with code **1** when validation fails (invalid flags, missing config, unknown package). <Terminology title="continuous integration and deployment" to="/docs/quickstart/terminology#builds-and-tooling" color={true}>CI</Terminology> pipelines that use this command will fail the step on errors.
:::

### UNRELEASED Sentinel Convention

When you add or change a public API member, tag it with the literal sentinel `@since UNRELEASED` (or `@deprecated UNRELEASED`) rather than a hand-written version number. The release step stamps the real version at release time, so you never have to guess or update the tag manually.

- Write `@since UNRELEASED` for new members and `@deprecated UNRELEASED` for members being deprecated.
- Never write a concrete version (e.g., `@since 1.3.0`) for unreleased code — it will be wrong if the bump type changes before release.
- Concrete versions are only appropriate for members that have already shipped in a published release.

```ts title="src/my-feature.ts"
// Before release (what you write):

/**
 * Returns the current config version.
 *
 * @since UNRELEASED
 */
export function getConfigVersion(): string { ... }

// After `nova utility changelog --release` (what gets stamped):

/**
 * Returns the current config version.
 *
 * @since 1.4.0
 */
export function getConfigVersion(): string { ... }
```

### Entry File Format

Each recorded change is stored as an individual `.md` file in `.changelog/`:

```markdown title=".changelog/brave-cats-jump.md"
---
package: "@cbnventures/nova"
category: added
bump: minor
---

New ESLint rule for switch case blocks.
```

### CalVer Mode

When `settings.versionStrategy` is `"calver"` in <Terminology title="Nova config" to="/docs/quickstart/terminology#nova-concepts" color={true}>`nova.config.json`</Terminology>, the changelog command switches to calendar-based versioning:

- **Version format:** `YYYY.MM.MICRO` — full year, unpadded month, micro counter that resets each new month.
- **No bump field:** Changelog entries omit the `bump` field entirely. The `--bump` flag is not available in CalVer mode.
- **Automatic version:** `--release` computes the version from today's date with no user prompt. If the current version shares the same year and month, the micro counter increments. Otherwise, the micro resets to `0`.
- **Current-version validation:** A workspace must already use `YYYY.MM.MICRO`, or the initial `0.0.0` sentinel before its first release. Nova rejects invalid numbers and dates later than the current month before calculating the next version.
- **Heading format:** CalVer changelog headings omit the date suffix since the date is already embedded in the version number.

```markdown title=".changelog/brave-cats-jump.md"
---
package: "demo-envoy"
category: added
---

Added dark mode support.
```

```markdown title="templates/demo-envoy/CHANGELOG.md"
# demo-envoy

## 2026.8.0

### ADDED
- Added dark mode support.
```

#### Strategy Lock

Before the initializer opens or the changelog command records or releases a change, Nova scans the root `CHANGELOG.md` and every non-freezable workspace's `CHANGELOG.md`. Existing version headings lock `settings.versionStrategy` to the strategy already used by the project. Valid SemVer prerelease and build metadata remain part of SemVer history. Missing changelog files and freezable workspaces are ignored.

Nova stops with a non-zero exit code when the configured strategy conflicts with that history, when the project mixes SemVer and CalVer release headings, or when a numeric release heading does not match either supported format. A project with no release headings remains unlocked, so the initializer can still change its strategy.

### CHANGELOG.md Format

Released entries are written in the following format. Headings are ordered as UPDATED, FIXED, ADDED, REMOVED.

Empty headings are omitted. When lock-step versioning is enabled and a package had no recorded changes, the version section contains "No changes." instead of category headings.

```markdown title="packages/nova/CHANGELOG.md"
# @cbnventures/nova

## 1.3.0 - 2026-02-25

### FIXED
- Crash in initialize command.

### ADDED
- New ESLint rule for switch case blocks.
```

```markdown title="packages/docusaurus-preset-nova/CHANGELOG.md (lock-step, no changes)"
# @cbnventures/docusaurus-preset-nova

## 1.3.0 - 2026-02-25

No changes.
```

## Migration from Changesets

For users migrating from the [Changesets](https://github.com/changesets/changesets) workflow, Nova provides equivalent flags under `nova utility changelog`:

| Command                            | Equivalent          | What It Does                                                                                            |
|------------------------------------|---------------------|---------------------------------------------------------------------------------------------------------|
| `nova utility changelog --record`  | `changeset add`     | Record a change with `-p`, `-c`, `-b`, `-m` flags.                                                      |
| `nova utility changelog --release` | `changeset version` | Release accumulated changes, bump versions, and stamp `@since`/`@deprecated UNRELEASED` tags in source. |

:::tip Shorten long commands with scripts
Nova bundles many tools in one package, so commands can be verbose. Shorten them by adding aliases to the `"scripts"` field in your **root** `package.json` (the one at the <Terminology title="project root" to="/docs/quickstart/terminology#git-and-workflow" color={true}>monorepo root</Terminology>):

```json title="package.json"
{
  "scripts": {
    "changelog:record": "nova utility changelog --record",
    "changelog:release": "nova utility changelog --release"
  }
}
```

Then run `npm run changelog:record` or `npm run changelog:release`.
:::

## Troubleshooting

- **"No eligible (non-freezable) workspaces found"** — Confirm that <Terminology title="Nova config" to="/docs/quickstart/terminology#nova-concepts" color={true}>`nova.config.json`</Terminology> has at least one <Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspace</Terminology> with a <Terminology title="private workspace" to="/docs/quickstart/terminology#nova-concepts" color={true}>trackable</Terminology> or <Terminology title="publishable workspace" to="/docs/quickstart/terminology#nova-concepts" color={true}>distributable</Terminology> <Terminology title="workspace label" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspace policy</Terminology>.
- **"Cannot use --record and --release together"** — These flags are mutually exclusive. Run them as separate commands.
- **"Non-interactive record requires --package, --category, --bump, and --message"** — In semver mode, all four flags are required when using `--record`. In CalVer mode, only `--package`, `--category`, and `--message` are required (no `--bump`). Omit `--record` for interactive mode.
- **"No changelog entries found"** — The `.changelog/` directory is empty or does not exist. No versions or changelogs change, but a non-dry-run release still stamps freezable workspace sentinels at `0.0.0`.
- **"Package not found in nova.config.json"** — The `--package` value must match the `name` field of a non-<Terminology title="locked workspace" to="/docs/quickstart/terminology#nova-concepts" color={true}>freezable</Terminology> <Terminology title="package" to="/docs/quickstart/terminology#nova-concepts" color={true}>workspace</Terminology> in <Terminology title="Nova config" to="/docs/quickstart/terminology#nova-concepts" color={true}>`nova.config.json`</Terminology>.
- **"Configured version strategy ... conflicts with existing ... release history"** — Keep `settings.versionStrategy` aligned with the format already recorded in the root or a non-freezable workspace changelog. Do not rewrite published history merely to switch strategies.
- **"Lock-step versioning requires every non-freezable workspace to start at the same version"** — Align the listed workspace versions, then run the release again. Nova has not written any release files when this check fails.
- **"UNRELEASED sentinel survived stamping"** — The release step found a supported `@since UNRELEASED` or `@deprecated UNRELEASED` tag in a workspace's `src/` or `scripts/` tree that was not replaced. Check the file paths in the error, correct the source problem, and re-run the release; pending entry files remain available.
